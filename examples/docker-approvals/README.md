# docker-approvals — human-in-the-loop tool gates

Deploys one agent (`approvals-agent`) plus the `panel` channel over the NATS
transport. The agent has two tools in a single skill:

- `read_status` — runs freely, no gate.
- `restart_service` — destructive, so the skill declares
  `needs_approval=["restart_service"]`. The runtime parks the turn (via a
  LangGraph `interrupt()`, checkpointed durably) before the tool executes,
  and only runs it once a human approves.

An optional, commented-out Slack channel block in `vystak.py` exercises the
same gate over Slack's Block Kit approve/deny buttons. It's off by default —
the panel-only deploy is what `vystak apply` gives you out of the box.

## How the approval gate works

When the model calls `restart_service`, the wrapped tool raises an
`interrupt()` with `{kind: "tool_approval", tool, args, skill}` before the
underlying function runs. The turn is checkpointed at that point and the
panel (or Slack) surfaces it as a pending decision. A human's Approve/Deny
click resumes the graph with `{approved: bool, decided_by: str, note: str |
None}`; on approve, `restart_service` actually runs and the turn continues;
on deny, the tool call is short-circuited to `"Denied by {who}: {note}"` and
the agent continues without ever having restarted anything.

Because the park is a checkpoint like any other turn state, it survives
closing the browser tab and it survives an agent container restart — the
decision is still waiting whenever a human gets to it. Only the first
decision counts: if two people click at once, the second sees the turn is
already resolved.

## This example cannot run concurrently with other panel examples

`examples/docker-panel`, `examples/docker-panel-nats`, and
`examples/docker-panel-durable` all bind host port 18100 and deploy an
unnamespaced `vystak-channel-panel` container. Destroy one before deploying
another (including this one).

## Deploy the stack

This project ships without the generated `_vystak/` runtime snapshot (see
"Generated files" below), so scaffold it first:

    cd examples/docker-approvals
    cp .env.example .env   # fill in your real ANTHROPIC_API_KEY
    export PANEL_SERVICE_TOKEN=$(openssl rand -hex 24)

    vystak init --framework langchain-python --force .   # scaffolds _vystak/ + template boilerplate

`vystak init --force` overwrites this directory's `README.md`, `server.py`,
`Dockerfile`, `pyproject.toml`, `requirements.txt`, and `.env.example` with
the current bundled template's defaults, and it also **drops a fresh
`vystak.yaml`** even though this project's config lives in `vystak.py`.
`vystak`'s convention-file search order is `vystak.yaml`, `vystak.yml`,
`vystak.py`, so a stray `vystak.yaml` silently wins and `vystak plan` reports
a generic `example-agent` instead of `approvals-agent`. After scaffolding,
restore the tracked files and remove the stray config:

    git checkout -- README.md server.py Dockerfile pyproject.toml requirements.txt .env.example
    rm -f vystak.yaml

Then:

    vystak plan     # shows the agent and panel channel deployments
    vystak apply

The panel API is now at http://localhost:18100 (try `GET /health`).

## Generated files

`_vystak/` (the runtime template snapshot), `.vystak/` (local deploy-side
state), `.env`, and `uv.lock` are not committed — they're regenerated by
`vystak init`. Only `vystak.py`, `tools/`, `README.md`, `.env.example`,
`Dockerfile`, `pyproject.toml`, `requirements.txt`, and `server.py` are
tracked.

## Run the control panel UI

The UI is the `vystak-panel` Next.js app (not deployed by `vystak apply`):

    cd ../../packages/typescript/vystak-panel   # from examples/docker-approvals
    cp .env.example .env.local   # fill in:
    #   PANEL_API_URL=http://localhost:18100
    #   PANEL_SERVICE_TOKEN=<same value as above>
    #   AUTH_SECRET=$(openssl rand -base64 32)
    #   AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET from your Google OAuth client
    pnpm --filter vystak-panel dev

Open http://localhost:3000 — the first Google account to sign in becomes the
admin; invite others from /admin/users.

### Password sign-in

To enable email+password authentication alongside Google OAuth, set
`PANEL_PASSWORD_AUTH=1` in the panel app's environment (`.env.local`). The
first admin still bootstraps via Google (or the channel API); after that, any
admin can set passwords for other users from the admin Users page.

## Walkthrough: approve a gated tool call in the panel

1. In the panel UI, start a new conversation with `approvals-agent` and send:

       the web service looks broken — fix it

2. The agent calls `read_status` first — this one is ungated, so you'll see
   it run and its result appear in the transcript immediately (`service web
   is DOWN...`).

3. The agent then proposes `restart_service` with the model-chosen argument
   (e.g. `name="web"`). Because this tool is in the skill's
   `needs_approval` list, the turn parks: the panel shows an **Awaiting
   Approval** card naming the tool and the args the model chose, with
   Approve/Deny buttons and an optional note field.

4. Click **Approve**. The tool runs, `restart_service` returns its result,
   and the turn continues live — the agent summarizes and the final reply
   lands in the same conversation, no page reload needed (this relies on the
   NATS transport to push the resumed turn back to the browser).

5. Start a **new** conversation and repeat the same prompt. This time click
   **Deny** (optionally with a note, e.g. "not during business hours"). The
   agent does not restart anything — its next message reports that it
   couldn't proceed, and its reasoning references `Denied by <you>: <note>`.

6. To see the durability of the park: send the prompt again, and once the
   Awaiting Approval card appears, close the browser tab entirely (or
   restart the agent container with `docker restart
   vystak-approvals-agent`). Reopen the panel and navigate back to that
   conversation — the approval card is still there, unresolved, waiting for
   a decision. Nothing about the pending approval is lost by a browser close
   or an agent restart.

If two people click Approve/Deny on the same card, only the first click
takes effect — the second person's click is met with an "already resolved"
response, and the transcript reflects whichever decision landed first.

## Walkthrough: Slack (optional)

Slack support requires a Slack app with Socket Mode enabled, plus
`SLACK_BOT_TOKEN` (`xoxb-...`) and `SLACK_APP_TOKEN` (`xapp-...`) — see
`examples/docker-slack/vystak.py` for the required scopes and event
subscriptions. To try it:

1. Uncomment the `slack` channel block at the bottom of `vystak.py`.
2. Export the two Slack tokens alongside `PANEL_SERVICE_TOKEN` before
   `vystak apply`, or add them to `.env`.
3. `vystak apply`, then invite the bot to a channel and send the same
   prompt as above.
4. `read_status` runs immediately; when the agent proposes
   `restart_service`, the bot posts a Block Kit message with Approve/Deny
   buttons naming the tool and args. Clicking a button flips the message to
   "Approved by @you" or "Denied by @you", and the agent's final reply lands
   in-thread.
5. Sending a second fix request in the same thread that again needs
   `restart_service` chains a new approval message — each gated call gets
   its own card, resolved independently.

This works the same way whether the agent is running the default streaming
protocol or `a2a-turn`.

## Verify `needs_approval` is validated at plan time

`needs_approval` entries must name a tool that's actually in the skill's
`tools` list. To see this fail fast: edit `vystak.py` and change

    needs_approval=["restart_service"]

to something like

    needs_approval=["restart_service", "not_a_real_tool"]

then run `vystak plan` — it should error out with a message naming the
unknown tool, before anything gets deployed. Revert the edit afterward.
